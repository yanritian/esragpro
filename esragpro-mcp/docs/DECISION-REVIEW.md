# esRAGPro MCP 与企业知识图谱方案决策审查

## 1. 文档目的与结论

本文记录 2026-07-10 对以下材料的产品与架构决策审查。它回答三个问题：原方案哪些思想应保留，哪些定义必须修正，哪些路线应明确否决。

结论：原方案在混合检索、证据追溯、领域本体、抽取审核、冲突检测、评测和离线交付方面方向正确；主要问题是把“本地单人 Rust 工具”与“企业级多租户知识库”混成一个产品，并让 MCP、索引或 LLM 抽取结果承担了不应承担的数据真源职责。

已确认的目标路线是：

1. 一个知识核心，Enterprise Edition 与 Local Edge Edition 两种交付形态。
2. Enterprise 以 PostgreSQL 和对象存储为系统记录，Elasticsearch 与 Neo4j 为可重建投影。
3. MCP 是安全协议适配层，不建立第二套企业数据面。
4. Enterprise 先行；Local Edge 在领域契约、证据契约和评测集稳定后启动。
5. 图谱事实采用候选、校验、审核、发布、替代和失效生命周期。

本文只记录设计结论，不表示相应代码已经实现。

## 3. 保留的原方案内容

### R-01 混合检索作为默认检索基础

**决定：保留。** BM25 处理精确术语，向量检索处理语义改写，两者互补。图谱用于复杂关系问题的增量召回，不替代原文检索。

**修订后的落点：** BM25 与向量并行召回，条件触发图检索，统一融合后重排；响应记录实际路由与降级。证据见 E-16、E-17，以及现有 `backend/app/core/elasticsearch.py` 的混合检索基础。

### R-02 证据可追溯与拒绝回答

**决定：保留并提升为硬契约。** 每个检索结果、图谱边、声明和答案引用都必须指向不可歧义的 `evidence_id`，并可解析到文档版本和原文位置。无证据、证据冲突或证据权限失效时必须缩小范围、警告或拒绝。

**理由：** `kg` 方法论明确要求来源、风险与拒绝，但脚手架没有兑现，见 E-17、E-18、E-19、E-21。因此本次不是删除思路，而是把它从提示词要求提升为数据与验收要求。

### R-03 领域本体与领域适配

**决定：保留。** 实体类型、关系类型、别名规则、抽取约束、问题改写和回答政策应集中版本化，避免散落在代码与提示词中。

**修订后的落点：** 本体成为知识库级版本资源；事实记录本体版本，升级可迁移和回滚。证据见 `kg\SKILL.md:72-79` 和 `kg\references\project-blueprint.md:9-15`。

### R-04 异步摄取、抽取缓存与人工审核

**决定：保留并设为企业必需能力。** 摄取必须有任务、进度、重试、幂等和逐文件结果；抽取结果先保存为候选，用户审核后才发布图谱事实。

**理由：** `kg` 方法论已经提出任务跟踪、抽取缓存和导入前审核，见 E-16；其脚手架却仍直接入图，见 E-20。本方案采用方法论，不复制缺少审核的实现。

### R-05 冲突检测、离线评测与失败回退

**决定：保留。** 冲突检测用于发现互斥证据、时态差异和术语重复，不自动裁决业务事实；评测放在离线或 CI 流程；LLM 不可用时返回匹配证据与清晰降级状态。

**证据：** E-16、E-17。

### R-06 Local Edge 与离线模型方向

**决定：保留为后续交付形态。** 单二进制、嵌入式存储、本地模型和 stdio 对隔离网与个人场景有价值，但不能据此定义 Enterprise 的多租户数据面。

**证据：** 原始 PRD 基线 E-01 与 `kg\SKILL.md:79,104-110` 都显示明确离线需求；该需求被重新排序，而非否定。

### R-07 MCP 作为智能体入口

**决定：保留。** MCP 适合把企业知识能力以可发现 Schema 暴露给智能体。完整性必须包括 Tools、Resources、Prompts、授权、分页、取消、错误、传输和兼容测试，而非只列十个名称。

**证据：** E-04 至 E-08 说明当前只有入口意图，没有协议实现；因此保留产品入口，重做能力边界。

## 4. 必须修正的内容

### C-01 从“两个知识引擎”修正为“一个知识核心、两种交付形态”

**原问题：** 原始 PRD 把 esRAGPro Web 与 Rust MCP 描述成 ES/PG/Neo4j 对 LanceDB/SQLite 的两套平行产品，会产生双写、权限漂移、删除不一致和重复评测。

**修正：** Enterprise 的 Web、REST 和 MCP 共用知识核心；Local Edge 只在后续复用领域契约与评测集。Enterprise MCP 不维护独立索引或图数据库。证据见 E-01、E-07、E-15。

### C-02 明确权威记录与查询投影

**原问题：** 当前文档列表和删除直接依赖 ES/Neo4j，原件仅保存在本地目录，无法可靠回答“哪个版本、谁授权、何时删除、投影是否完成”。证据见 E-10、E-11。

**修正：** PostgreSQL 保存文档元数据、版本、ACL、任务、候选事实、审核和审计；对象存储保存原件；ES 与 Neo4j 通过版本化事件构建，可重建且不得扩大权威权限。

### C-03 从固定串行“五层检索”修正为自动路由与并行召回

**原问题：** 每个问题都串行经过关键词改写、全文、向量、图扩展和路径排序，会增加延迟、错误面和无关图噪声；`fast/standard/deep` 把底层实现暴露给调用者。

**修正：** BM25 与向量并行，图检索按意图和策略触发，融合后重排。调用者只选择业务级检索策略，系统返回实际路由和降级原因。现有空向量与空图查询进一步说明需要先建立正确基线，见 E-12。

### C-04 从“模型抽取即事实”修正为事实治理生命周期

**原问题：** 模型抽取直接入图，证据在去重与写图时丢失，见 E-18 至 E-20。

**修正：** 抽取只生成候选；候选经过 Schema 校验、实体消歧、证据校验、冲突检测和人工审核后发布。事实保留有效时间、记录时间、来源版本、审核决定和替代链。

### C-05 从十个混合 Tool 修正为完整 MCP 能力面

**原问题：** `search`、`ingest`、`verify`、`reason`、`evaluate`、`get_document`、`list_documents`、`delete_document` 和 `stats` 混合了查询、资源读取、评测和高风险管理；代码 Schema 仍为空，见 E-05。

**修正：**

- 默认 Tools：证据检索、证据回答、实体查询、邻居扩展、路径查询、声明核验。
- Resources：文档版本、证据、实体、本体、任务与能力说明。
- Prompts：带引用回答、证据比较、需求追踪和声明核验。
- 运维 Tools：单独配置档、默认关闭，只发起有范围和可审计的任务或审批请求。
- 评测：离线或 CI 能力，不占用默认智能体工具面。

### C-06 从旧式 SSE 修正为 Streamable HTTP

**原问题：** 原架构把 SSE 作为团队共享传输，见 E-02；本地骨架依赖只启用 `transport-io`，见 `Cargo.toml:14-18`。

**修正：** Local Edge 使用 stdio；Enterprise 使用 Streamable HTTP，并完成身份、会话、取消、超时与断线测试。stdio 标准输出只允许协议帧，现有输出行为必须修复，见 E-04。

### C-07 从“本地不认证”修正为端到端企业授权

**原问题：** 原计划明确不做认证；现有上传、删除和图谱管理接口也没有绑定授权，注册还存在角色自授风险，见 E-03、E-09、E-13、E-14。

**修正：** 远程 MCP 使用企业身份或受管服务身份；授权覆盖租户、知识库、文档和 Tool Scope；检索前过滤，Resource 读取再次授权，缓存键包含权限版本；破坏性操作审批并审计。

### C-08 从“通用性能与幻觉口号”修正为可复现质量门禁

**原问题：** 原始 PRD 在没有测试、容量档位和数据集的情况下给出冷启动、内存、索引速度、十万文档延迟及防护比例。E-08 证明当前没有验证这些数字的测试资产。

**修正：** 目标数值必须绑定硬件、语料、并发、模型、索引版本和测试区间；可信质量分别报告检索召回、图谱增益、引用完整性、声明支撑和拒绝质量，不使用单一“幻觉率”。

### C-09 从远程 `ingest(path)` 修正为受权上传引用

**原问题：** 远程智能体传入服务端路径既不可移植，又产生路径遍历和越权读取风险。

**修正：** Enterprise 摄取主要通过管理 Web/REST；可选 MCP 运维 Tool 只接受 Core upload-session create/content/finalize 闭环签发、绑定 tenant/subject/KB 且短期单次消费的 `source_ref`。消费 ref、创建 Job 和 outbox 必须同事务，回滚不得丢失 ref。任意本地路径仅可在未来 Local Edge 中按目录白名单使用。

### C-10 先修复现有知识核心，再接 MCP Gateway

**原问题：** 现有上传调用不存在的方法、图查询固定为空、查询向量为空、关键接口无授权，见 E-09、E-12、E-13、E-14。薄 Gateway 若直接透传，只会把缺陷扩大到智能体。

**修正：** 实施顺序必须先建立可测试的领域 API、权威记录和 ACL，再交付 MCP；Gateway 的完成不能早于后端安全与证据契约完成。

## 5. 明确否决的内容

### X-01 否决 Enterprise MCP 自建独立企业数据真源

不在 Enterprise Gateway 中维护 LanceDB + SQLite 的另一份文档、向量和图谱真相。理由是双写、权限、删除、审计和恢复无法形成单一责任边界。E-07 显示当前依赖方向正走向第二数据面，因此必须停止扩展该路线。

### X-02 否决当前阶段全面 Rust 重写企业核心

Rust 可用于未来 Local Edge 或经数据证明的性能关键组件，但当前不重写用户、ACL、文档版本、任务、审核、审计、ES 和 Neo4j 领域逻辑。重写不能替代先修复现有后端与建立验收基线。

### X-03 否决模型输出、相似度或路径直接成为事实

模型置信信息只用于排序候选；相似度只表示匹配；图路径只表示已检索关系链。三者都必须由证据、规则和审核决定其可发布状态。E-18 至 E-21 说明缺少这些约束会产生看似完整但不可追溯的结果。

### X-04 否决默认暴露破坏性与评测 Tool

直接 `delete_document`、清空图谱、修改 ACL 和全库 `evaluate` 不进入默认智能体能力。删除改为审批请求，评测进入离线或 CI，统计进入受权管理面或 Resource。

### X-05 否决用 Prompt 代替数据与权限控制

“必须基于文档回答”“禁止编造”等 Prompt 可以保留，但不能代替证据外键、引用校验、召回前 ACL、声明核验和拒绝状态。E-18、E-19、E-21 已证明提示词要求会在后续代码路径中丢失。

### X-06 否决把 Enterprise 描述为零依赖单机产品

Enterprise 的目标是可信、多租户、可审计、可恢复；它需要明确的权威存储、投影、身份和运维能力。“零外部服务”只属于未来 Local Edge 的部署价值，不是 Enterprise 的成功标准。

### X-07 否决把当前 Rust 骨架描述为 MCP MVP

当前 Server、Schema、检索、摄取、事实核查和测试均未实现，且 stdio 输出与模块声明存在基础问题，见 E-04 至 E-08。文档和交付状态必须如实标记为设计/骨架，直到协议与端到端测试通过。

## 6. 对实施的约束

后续 Claude Code 或 Qwen 执行时必须遵守以下约束：

1. 不新增第二套 Enterprise 文档或图谱真源。
2. 不在领域 API 与 ACL 可测试前扩展 MCP Tool 数量。
3. 不让候选事实绕过证据校验和审核进入默认图检索。
4. 不把检索后裁剪当作权限过滤。
5. 不以演示成功、接口返回 200 或工具可发现替代质量门禁。
6. 不声明未经可复现报告验证的性能和可信比例。
7. 每个阶段必须同时提交实现、自动化测试、数据迁移/回滚说明和状态文档。
8. 实施计划、架构和检索设计若与本决策冲突，以本文件和 PRD 的产品边界为准，并先显式更新决策记录。
