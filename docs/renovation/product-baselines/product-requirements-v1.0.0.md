## 1. 产品目的、角色与端到端旅程（A）

### 1.1 产品目的

让业主以更低的设计门槛和更可控的成本理解自己的家：能独立决定半包范围，能自由编辑方案并看懂每一笔费用，能把可追溯的方案交给施工方，并在入住后继续使用同一份家庭空间信息。长期形态是“装修设计 → 施工交付 → 入住使用”围绕同一份 canonical 版本场景持续演进，而不是每个阶段重建一套房子。

### 1.2 角色

| 角色 | 主要诉求 | 权限边界 |
| --- | --- | --- |
| 业主（主用户） | 低门槛表达需求、自由编辑、看懂预算、掌握半包决策、保留方案与数据 | 最终确认需求与方案；可撤销代理建议；数据可备份/导出 |
| 家庭成员 | 参与生活习惯、无障碍、收纳与审美偏好表达 | 通过业主可见的确认流程进入需求集；不直接改写工程结论 |
| 设计师/顾问 | 在同一场景中复核与完善方案、解释变更 | 建议与编辑需留痕；不得覆盖业主已冻结的硬约束 |
| 施工方/工长 | 读取工程量、范围、任务与变更；提交施工变更申请与交付记录 | 不静默改设计；变更须走申请/审批；不得自动确认安全项 |
| 专业复核者（结构/水电/暖通/监理） | 对承重、拆改、机电、施工可行性给出人工确认 | 只能人工签核；系统不得代替或自动完成 |
| 产品评审/发布方（Codex 等） | 独立评审、验收裁决、发布与知识入库 | 不由实现 worker 自任；不把文档等同验收 |

### 1.3 端到端旅程

- **J1 全旅程（最终目标）**：需求采集与原话留证 → 户型/尺寸真值确认 → 方案编辑与实时人尺度体验 → 预算与半包范围 → 施工交付、变更与人工签核 → 入住后的设备模拟与（未来）真实家庭映射 → 持续使用同一 `home_id` 空间。
- **J2 近期主线（尚未完成）**：编辑一间房 → 以人尺度第一人称进入 → 模拟灯/窗帘 → 保存并重开一致。当前只有未接线、未完成的约 21 KB `walkthrough_coordinator.gd`；第一人称、运行时、状态与面板均未完成。
- **J3 变更旅程**：业主提出变更 → 系统展示对需求/工程量/预算/施工的影响 → 业主确认或调整 → 形成新版本 → 交付记录与回滚点。变更不得静默覆盖旧版本。
- **J4 入住旅程（明确延后，不缩小范围）**：先在无硬件条件下模拟设备与场景，再选择一个真实生态接入；设计态、竣工态、模拟态、观测/指令态始终分开。

> 三类旅程共同证明：当前原型只是本地样例，不是完整产品；S1 完成也不等于 J1 完成。

## 2. 两大产品支柱（B）

### 2.1 支柱一：实时、可编辑、可探索的家

用户在同一份版本化场景中移动、编辑、替换材质与家具，画面持续更新；目标视觉保真接近真实空间与质量渲染，而不是“点一下出一张图”。判定标准是**运行中的应用**在多个视点、连续交互下保持一致，而不是离线 PNG 的分辨率或单张成图。

### 2.2 支柱二：通过“已验证意图”收敛的需求理解代理

代理围绕业主原话、家庭画像、硬约束、预算与视觉参考逐步澄清，每次推断标注不确定性，经用户确认后冻结；后续生成可有变化，但已确认事实与约束必须稳定。它追求“理解并收敛”，而不是随机“再画一张图”。esRAG 负责召回来源可追溯的需求、决策与证据；它不凭空理解客户，也不替代几何/预算校验器。

### 2.3 支柱关系

需求理解给出“为什么这样设计”的可追溯依据；实时场景给出“设计出来是什么样”的可交互事实；预算/工程量给出“代价是什么”；版本与知识层保证三者可回查、可评审、可交付。任一支柱缺失，都不能称为完整产品。

### 2.4 可测性与证据等级约定

- 每条需求的验收必须落到四类检查之一：纯领域/数据 runner、进程内 UI/信号、独立进程持久化、打包产物在空目录的真实运行；视觉类还必须包含运行中的连续捕获。
- 证据等级：`E0` 无；`E1` 静态源码/文档；`E2` runner/JSON/日志/退出码；`E3` 真实进程、打包产物、GPU 捕获或独立进程重开。状态标“已实现”至少需要范围匹配的 `E2`；视觉与交付类至少需要 `E3`。
- 每个证据目录唯一，包含原始 stdout、stderr、退出码与机器可读报告；失败证据同样保留，不得删除或覆盖。证据中不得含凭据；客户授权范围内的私密项目数据须按项目隔离、最小化并在共享/公开证据中去标识化。
- 需求状态只能由独立评审更新；实现者自报、文档描述、计划文本均不改变状态（见 KNO-001/KNO-005）。本文件是“会话推导的实施基线”，不是用户逐条签核，也不是产品验收。

## 3. 视觉保真与实时体验（C / VIS）

保真目标按以下维度定义，而非单一“像不像照片”：整体房间光照、明暗与深度；近景几何厚度、接缝、织物/木/金属/玻璃质感；正确尺度；可信反射、接触阴影与间接光；多视点与连续交互一致；家具/材质替换前后的一致。实时视图、可选离线 Cycles 导出、参考图意图三者必须明确区分：离线渲染完成不等于实时支柱达成；参考图只表达偏好意图，不是可交付场景。

性能/分辨率/资产复杂度/质量基准/参考图集均**尚无用户确认数值**。任何帧率、分辨率、设备档位数字都是工程提案，精确阈值列入未决决策（OD-01、OD-02）。不得承诺 GTX 1060 上 4K/60fps/照片级；现有 GTX 1060 证据是离线 Cycles 1280×800/64 samples，不是实时基准。

### 3.1 视觉保真评审协议（工程提案，阈值待 OD-01）

- **参考集**：至少覆盖客厅、卧室、厨房的主视角与近景材质（织物、木、金属、玻璃），并记录参考图来源与授权；参考图只表达意图，不是验收成品。
- **视点矩阵**：入口视角、主视角、近景、逆光、窗边、低/高视角；每个视点记录相机位姿、场景 revision、设备、渲染设置与时间。
- **比较维度**：光照方向与色温、遮蔽/接触阴影、反射可信度、材质尺度、接缝与厚度、噪点/锯齿、帧间稳定性、物体比例。
- **通过规则**：不得用单张最佳图代表整体；阻断级缺陷一票否决，重要/次要缺陷记录并给出修复项；具体分数线由 OD-01 确认后冻结为版本化阈值。
- **缺陷分级**：阻断（穿模、漏光、尺度错误、崩溃、明显跳变）；重要（材质/阴影明显失真）；次要（可记录、可延后）。

## 4. 需求理解、确认与变更闭环（D / INT）

代理必须保留业主原话与证据，结构化家庭/生活方式/ routines/无障碍/功能需求，区分硬约束、软偏好与未知；记录预算与包含项；对视觉参考做分解（喜欢的颜色 ≠ 喜欢的形状/材质/装饰/布局/光线）；只做小步、针对性澄清；对不确定推断显式标注；经用户确认后冻结；冲突必须披露；每次设计变更解释其对应的需求依据；局部编辑尊重已锁定对象；记录拒绝与否定偏好；支持撤销/版本历史；反馈细化只针对当前家庭，不假设所有客户口味相同。

esRAG 召回来源可追溯的证据与已确认决策；它不是“读心术”，也不替代几何、预算与规范校验。生成式提案可以变化，但已确认事实、硬约束与预算边界必须稳定；任何生成结果不得自动升级为确认事实。

## 6. Canonical 场景与 BIM 信息底座（F / SCN）

项目/家庭/楼层/房间/对象使用稳定 ID；对象信息含几何、参数、材质、资产引用、关系、版本与来源。空间层级（家庭→楼层→房间）与装修专业分类（建筑基底、隐蔽机电、土建/暖通/围护、硬装、软装、家具家电）是两套正交的轴，不得混为同一层级。

## 7. 编辑能力（G / EDT）

目标编辑能力：房间/墙体/开口；对象放置、吸附、旋转、尺寸、材质；替换/新增/复制/删除/锁定/自定义形状；资产类别与风格选择；表面照片材质（墙面/地面）；家具照片+尺寸辅助的可编辑网格重建；GLB 导入；材质贴图；来源与许可记录；对不可见表面（如墙后）做推断重建时标注“推断/近似”。**表面照片材质与家具照片建模是两条不同路径**：前者产出贴图/UV 与尺度，不产出家具几何；后者必须在照片之外结合真实尺寸创建或导入可编辑网格。任意单张照片的精确重建不作保证。

### 7.1 编辑事务语义（工程提案）

- **操作类型**：创建、删除、变换、替换、材质、锁定/解锁、房间/墙体编辑、开口编辑；每类操作有独立校验器。
- **原子提交**：先校验候选（ID 唯一性、几何合法、材质签名、锁定状态、base 版本），全部通过后一次性提交；失败不得改变场景、文档或历史。
- **锁定语义**：锁定对象需显式解锁才能编辑；批量操作与生成式代理不得隐式解锁；冲突时列出被锁定对象。
- **预览分离**：预览、模拟、候选渲染不产生 canonical 变更；用户显式“应用”才生成操作与版本。
- **历史语义**：undo/redo 只作用于工作态；显式保存生成不可变 revision；载入历史会清空工作态历史；失败恢复保持内存与磁盘不变。

## 12. 版本化、写入与恢复协议（L）

采用 append-only 链路：`v1.0.0` → 变更提议 → 评审 delta → 新版本 → 任务 → 代码/产物/测试 → 评审裁决 → 知识写回。任何已发布版本、旧文件、旧方案与用户数据不得被覆盖；新版本以新文件和新 manifest 出现。写入前做乐观 base 版本/哈希校验，冲突变更拒绝；被取代的基线不得当作当前；查询按项目/版本隔离。

本地文件与 esRAG 全文本/分节记录同时存在，并有 publication manifest 与回读回执；检索或写入失败时显示失败状态，不得显示“已同步”。中断后从 checkpoint 恢复，不重复创建 worker、不重复调用 API。

### 12.1 中断恢复检查点协议（工程提案）

- checkpoint 至少记录：任务 ID、基线 ID/版本/哈希、拥有路径、当前阶段、已完成产物及其哈希、证据路径、待办动作、worker/API 调用台账。
- 恢复前先校验基线哈希与已声明产物哈希；不一致时停止并报告，不得覆盖或“修复”未知变更。
- 已完成步骤以证据为准跳过；不得重复创建 worker、重复提交渲染/API 任务或产生重复 revision。
- checkpoint 写入证据目录，不写入产品数据、默认用户目录或知识库。
- 恢复动作与结果写入回执；中断本身不改变需求状态或验收结论。

### 12.3 需求版本变更与实现状态更新分离（评审补充）

- 已发布 PRD 快照是不可变文件；其中“当前状态矩阵”是**发布时点**的快照，仅供回溯，不随后续代码进展自动更新。
