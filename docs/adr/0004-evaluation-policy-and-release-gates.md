# ADR 0004: 评测策略和发布门禁

## 状态

已批准 (Approved)

## 上下文

esRAGPro 需要可测量的质量门禁，避免未经评测的性能和可信承诺。

原始方案（PRD.md E-01）给出未经测试的固定数字（"幻觉率 3-5%"、"延迟 XX 毫秒"），违反科学测量原则。

现有测试（backend/tests）：
- pytest 未安装，无法运行测试
- 没有固定的评测数据集
- 没有 golden set 和 holdout set 分离

## 决策

采用**可复现评测和发布门禁**架构：

### 1. 数据集分离

```
train/dev set    → WP5 用于调参
sealed holdout   → WP8 用于发布验收
```

**仓库只保存**：
- holdout manifest（数据集 ID、分层计数、corpus hash）
- evaluator 公钥
- 评测策略版本

**不保存**：
- 问题文本
- 期望答案
- 证据标签
- 阈值判定细节

**独立 evaluator**：
- 持有实际 holdout 样本
- 接收 artifact/schema/policy hash
- 返回签名报告

### 2. 必测维度

| 维度 | 指标 | 发布阈值 |
|------|------|---------|
| 检索 | Recall@20 | ≥ BM25 基线 +5% |
| 图谱 | 多跳命中率 | ≥ 非图方案 +5% |
| 引用 | Citation precision | = 1.00 |
| 声明 | 证据支撑 precision | ≥ 0.95 |
| 拒答 | F1 | ≥ 0.85 |
| ACL | 跨租户泄漏 | = 0 |
| 性能 | P95 延迟 | ≤ 2s (search) |
| 恢复 | RPO | ≤ 15 min |

**禁止**：
- 降低阈值来通过门禁
- 删除失败样本
- 混用 train/dev 和 holdout

### 3. 报告要求

每次报告必须包含：
- 硬件配置、语料规模、并发数
- 模型、索引、策略版本
- 预热条件和测量区间
- 失败案例分析

**禁止**：
- 单一"幻觉率"数字替代多维指标
- 缺少上述信息的性能结论

### 4. 发布门禁清单

WP8 必须通过以下所有门禁：

| 门禁 | 验证项 |
|------|--------|
| 契约 | Schema 兼容测试通过 |
| 代码 | 单元/集成/E2E 测试通过 |
| 协议 | stdio/HTTP 兼容测试通过 |
| 安全 | ACL 注入对抗集通过 |
| 数据 | 权威记录→投影一致性通过 |
| 质量 | holdout 阈值全部达标 |
| 运维 | 监控/备份/恢复演练通过 |

**任一门禁失败**：
- 不得发布
- 不得降低标准
- 不得用版本号代替验收证据

### 5. 本地开发测试

开发期间可以：
- 使用 dev set 调参
- 运行单元/集成测试
- 执行性能基准

**不得**：
- 查看 holdout 问题或答案
- 为 holdout 样本写特定规则
- 修改 holdout 或 evaluator 版本来通过门禁

## 理由

### 为什么选择此方案

1. **科学测量**：避免未经测试的承诺
2. **防止过拟合**：train/dev/holdout 分离
3. **可复现**：所有报告包含完整上下文
4. **防止篡改**：独立 evaluator 和签名报告

### 替代方案及为何拒绝

**替代方案 1：单一数据集**
- ❌ 容易过拟合
- ❌ 无法验证泛化能力

**替代方案 2：公布 holdout 内容**
- ❌ 开发者会针对 holdout 调优
- ❌ 失去独立验证意义

## 后果

### 正面后果

1. 质量有可测量保证
2. 防止未经测试的发布
3. 评测可复现和审计
4. 阈值基于实际数据

### 负面后果

1. 需要维护独立 evaluator
2. 需要创建和管理数据集
3. 发布流程更严格

### 缓解措施

1. 使用 CI 自动运行评测
2. 提供数据集创建指南
3. 提供评测报告模板

## 遵守要求

后续所有工作包必须遵守：

1. **WP0-WP7**：不得宣称未经测试的性能或可信数字
2. **WP5**：创建 dev set 用于调参
3. **WP8**：创建 holdout set，通过独立 evaluator 验证
4. **所有 WP**：报告必须包含完整上下文信息
