# 设计思路（Design Rationale）

> 架构讲"是什么"，本文讲"**为什么**"——每个关键决策背后的约束、被否掉的
> 替代方案，以及我们承认的代价。判断一个架构好不好，不看它列了多少功能，
> 看它在两难时刻选择了什么。

---

## 1. 幻觉防护：为什么是"拒绝"而不是"尽力回答"

**决策**：证据不足时主动拒答（fail-closed），而不是降低置信度继续回答。

**被否方案**：让 LLM 自由发挥，用后置检测标记可疑内容（业界多数产品的做法）。

**理由**：企业知识库场景里，一次编造的合同条款比十次"我不知道"代价大得多。
RAG 系统的幻觉来自检索与生成之间的语义鸿沟——检索给了 80% 相关的片段，
LLM 会用流畅的语言补上剩下 20%。事前约束提示词只能压住一半（实测 20-40% → 10-20%），
剩下的一半必须靠**逐声明核查 + 拒绝机制**（→ 3-5%）。

**代价（我们承认）**：拒答率上升。用户会更多地听到"文档中没有足够信息"。
我们认为在企业场景这是正确的失败方式——**宁可诚实地无知，不可自信地胡说**。

## 2. 记忆写入：为什么用事务性 Outbox 而不是直接双写

**决策**：PostgreSQL 权威存储 + 事务内 outbox 事件 + 异步投影。

**被否方案**：
- *双写（PG 写完写 ES）*：第二步失败时数据永久不一致，没有重试依据。
- *PG 逻辑复制 / CDC*：引入 Debezium + Kafka 级别的运维复杂度，单机部署扛不住。
- *由应用层直接写所有存储*：写路径每加一种投影就多一个分布式事务。

**理由**：outbox 模式把"多存储最终一致"降级为"本地事务 + 至少一次投递"——
这是分布式系统里唯一不需要协调器的方案。权威数据永远只有 PG 一份，
ES/Neo4j/MinIO 的投影**可以随时删库重建**，这让换 embedding 模型、改 mapping、
灾难恢复都变成"重放一遍"而不是"数据抢救"。

**代价**：查询有秒级投影延迟；需要一个 worker 进程。
记忆检索对新鲜度的容忍度远高于对一致性的要求，这笔交易是划算的。

## 3. 时序世界记忆：为什么需要 valid-time

**决策**：记忆项带 event-time / captured-time 双时钟，支持"截至 T 时刻"的状态
快照查询，决策过程可序列化回放（sealed replay + 质量门）。

**触发场景**：真实组织里知识是会变的——制度 3 月改、6 月改回。
普通 RAG 的向量库里新版本覆盖旧版本，查询"5 月的制度是什么"会返回最新版，
**这是时间穿越，是企业审计场景的致命伤**。

**理由**：把"世界状态"建模为事件流（append-only），状态是事件在某个时间点的
投影——这是事件溯源在知识管理上的直接应用。它让"当时我们为什么这么决策"
变成可精确回答的问题，而不仅靠人脑记忆。

**代价**：存储膨胀（每个状态变更都是事件而非覆盖）；查询多一层时间维度。
缓解：事件按 captured-time 分桶、快照合并策略、过期归档。

## 4. MCP 网关：为什么是 Rust，为什么双传输

**决策**：网关用 Rust 独立实现；stdio 与 Streamable HTTP 双传输并存。

**Rust 的理由**：
1. 网关是**唯一直接吃不可信输入的网络组件**——内存安全在这里价值最大；
2. 协议翻译（Anthropic ↔ OpenAI ↔ Gemini 语义互译 + 流式）要求确定性的
   低延迟，GC 停顿在流式场景里用户可感；
3. 单二进制 9.6MB、零运行时依赖——agent 用户 `cargo build` 一次就能挂上
   任意客户端，不需要装 Python 环境或 Node。

**双传输的理由**：
- stdio：Claude Code / Codex 这类 CLI 天然一进程一会话，进程隔离干净、
  不依赖任何常驻服务，**客户端断开即回收**；
- HTTP：浏览器端、团队共享实例、以及"网关先于 Agent 启动"的场景需要
  一个稳定的单实例端点。
- 代价：两种传输要各自维护（HTTP 侧多一层认证中间件）。我们认为
  覆盖两种真实使用形态值得这个维护成本。

## 5. 认证：为什么企业用 JWT、本机用静态令牌

**决策**：同一份代码，两种认证模式按配置切换。

- 生产（配置了 OIDC Issuer）：完整 RS256 JWT 校验——kid 解码、JWKS 拉取、
  iss/aud/exp/nbf/sub 全量验证。企业内网里网关背后是整个知识库，认证不能省。
- 本机（未配 Issuer + 配置了 `ESRAGPRO_AUTH_TOKEN`）：恒时比较的静态共享令牌，
  返回合成 claims。

**理由**：单机开发者的威胁模型里，攻击面是"同机的其他进程"——恒时比较的
静态令牌足够；为个人使用强制搭一套 OIDC 是把企业成本强加给个人。
两种模式由"是否配置 Issuer"这个单一开关区分，代码路径共享，
静态令牌校验放在 JWT 解码之前，行为差异一目了然。

**代价**：静态令牌无法撤销单个会话（只能换令牌）。本机场景可接受。

## 6. 向量嵌入：为什么做成可插拔的四模式

**决策**：`local`(torch) / `ollama` / `qwen_api` / `zhipu_api` 四种 provider，
torch 做成可选扩展。

**触发教训**：最初 torch 是硬依赖——默认镜像 1.5GB+、进程常驻 600MB、
只有 1024 维一种选择。而**嵌入模型的计算需求与 Agent 后端的 IO 需求
完全不同生命周期**：嵌入只在入库时跑，后端 99% 时间在等 ES 和 LLM。

**理由**：把"嵌入在哪算"从后端解耦出去，后端回归它擅长的 IO 编排。
Ollama 模式让个人开发者用一块 6GB 老显卡跑起私有化全栈；
API 模式让企业用户零 GPU 部署；torch 模式保留给完全离线的极端场景。
四模式共享同一接口（维度校验 + 归一化），切换 provider 不改 mapping。

**代价**：远程模式每批 +50-150ms 网络延迟；不同实现的向量语义可能有
细微差异（切 provider 后建议重建索引）。

## 7. 检索融合：为什么是 RRF 而不是加权

**决策**：BM25 与向量检索用 Reciprocal Rank Fusion 融合。

**理由**：两种检索的分数**量纲不同**（BM25 是无上界饱和函数，余弦是 [-1,1]），
线性加权需要按语料分布调参，且每次换 embedding 模型都要重调。
RRF 只消费排名（score = Σ 1/(k+rank)，k=60），免调参、跨语料稳定，
是 ES 原生支持的标准做法。

**代价**：RRF 丢弃了分数的绝对信息——两个检索器都"非常有把握"和都"很勉强"
会得到相同的融合分。补充手段是重排层（reranker）负责精排，RRF 只负责粗融合。

## 8. 采集器：为什么轮询而不是 Hook 实时推送

**决策**：一个独立的字节偏移增量采集器，每 5 分钟轮询三类 Agent 会话文件。

**被否方案**：为每个 Agent 写 hook/extension 实时推送（Claude Code 的 Stop hook、
Codex 的 notify、PI 的 extension）。

**理由**：
1. 一个采集器覆盖全部 Agent——hook 要为每家写一份、随各家版本漂移各自维护；
2. 会话文件是 Agent 自己落盘的事实来源（source of truth），轮询它天然容错：
   Agent 崩溃、采集器崩溃都不丢数据，偏移不推进即可；
3. 部署面只有"一个计划任务"，没有侵入用户的 Agent 配置。

**代价**：最长 5 分钟延迟；JSONL 格式变化需要跟进解析器。
对"事后可检索的记忆"而言，分钟级延迟是可接受的。

## 9. 我们接受的三个不完美

开源架构诚实清单——这些是我们知道但暂未解决的问题：

1. **文档解析深度不足**：PyMuPDF + python-docx 只做文本级抽取，
   对扫描件、跨页表格、多栏混排的还原能力远弱于 RAGFlow 的 DeepDoc。
   计划接入 MinerU/DeepDoc 作为解析前端。
2. **真实数据集评测缺失**：评测框架（分类测试用例、报告、指标）已经齐了，
   但公开基准（LoCoMo 等）的数字还没跑。"幻觉率 3-5%"目前是架构推算目标，
   不是实验结论。
3. **记忆查询无 MCP 工具**：对话已入库，但网关的六个工具都是 kb/graph 检索——
   Agent 想检索自己的历史对话需要走 REST 或等 `memory.search` 工具上线。

不遮掩这些，是因为设计思路的最后一条是：**架构的先进性不能用来抵账
工程的欠账**——这两份账本我们分开记，也分开还。
